# Energy Assistant v1

Canonical types, limits and runtime guards: `src/contracts/energy-assistant.ts`. Session state is React component state, separate from existing planner DTOs and browser repositories.

## PDF extraction

`POST /api/energy-assistant/bill`, Node runtime, `Content-Type: application/pdf`, raw PDF bytes (not multipart/base64). Same-origin browser guard; no-store responses. Limit 4 MiB while streaming, `%PDF-` signature, 12 pages, 48,000 extracted characters and two concurrent parsers/process. Client checks `.pdf` extension and PDF/empty MIME and file size. Server independently checks content type, actual bytes and signature. Sequential unpdf/PDF.js text extraction has an asynchronous ten-second deadline and loading-task destruction; synchronous pathological parsing is not hard-isolated. Scanned/empty PDFs with fewer than eighty non-whitespace text characters are rejected, along with corrupt/password-protected files. No OCR or permanent upload storage.

Success `{ok:true,bill:Bill}`. Bill has twelve required nullable field keys: provider, periodStart, periodEnd, billingDays, consumptionKwh, totalAmountAud, usageRateAud, supplyDailyAud, tariffType, solarExportKwh, feedInCreditAud, otherCharges. Each is `{value:typedValue|null,evidence:string|null}`. Unknown requires both null; zero is a real value. Dates are valid ISO local dates, ordered start/end; explicit days integer 1–730. Numeric magnitudes capped at ten million; only totalAmountAud may be negative (a current-period net credit). Amounts AUD, imported/exported energy kWh, usage AUD/kWh, supply AUD/day, feed-in credit positive AUD magnitude. An optional canonical tariffComponents array (required array in the provider schema) holds separate kind, label, rateAudPerKwh, consumptionKwh, amountAud and evidence. Kinds include peak, shoulder, off-peak, controlled-load, anytime, solar-feed-in and other. Rates are never averaged; a single usage rate remains unknown when multiple import tariffs exist. Components are bill rows, not appliance consumption. Never confuse a balance/arrears with current-period total, meter register or solar export with imported consumption. No account/address/customer identifiers are requested.

Provider returns a strict structured object. Runtime validation rejects extra keys, invalid types/dates/ranges, incomplete/refused output and malformed fields. Excerpts (up to 240 characters) must match extracted text with whitespace equivalence only, preserving punctuation, digits and token order. Unsupported optional evidence is cleared to unknown; unsupported core evidence cannot proceed. Imported kWh plus explicit days or valid ordered dates are core; every other value may remain null. An excerpt match supports traceability, not semantic correctness; user review is required. Evidence-bearing extraction uses the existing Responses server configuration and `gpt-6-luna` with `store:false`. Raw bill text is sent to OpenAI; app storage policy does not override provider processing/retention policies. No raw prompt/output logs or content cache.

Failure `{ok:false,message}`: 403 origin, 415 content type, 413 byte limit, 422 unreadable/insufficient/extraction failure; 503 provider/processing failure. Messages distinguish invalid PDF, no readable digital text, readable text with insufficient bill details, and unavailable analysis service. Client timeout 60 seconds; bill provider timeout 35 seconds / 4,000 output tokens. Development stage diagnostics report page/character counts and concept flags without raw text or values. In-memory bytes/text become eligible for collection after request processing; no secure-erasure claim is made.

## Confirmation and household context

`ConfirmedBill = {bill, correctedFields:BillKey[], confirmed:true}` is page-local. Corrections validate the whole object, clear obsolete excerpts, and record changed keys as user-reported. Blank remains null; entered `0` remains zero. Saving edits does not confirm; the separate Confirm action snapshots values before analysis. No bill values modify bedroom facts or financial methods.

Deterministic days use explicit confirmed billingDays first. Otherwise use `(end-start)/86400000+1` (both endpoints included), only from valid confirmed dates, with displayed convention for review. `kWh/day = confirmed imported kWh / days`; unknown required inputs produce no figure. There is no annualisation, cost reconstruction or appliance estimate. All imported kWh remain unallocated, including zero distinctly from missing.

Question IDs: occupancy, loads, cooling, hotWater, dryer, pool, ev, refrigeration, solar, routine, priority. Bill conversation state separately retains `asked` substantive IDs, the current question and its optional clarification. Maximum five substantive slots, counted when a question opens; inferred facts and clarification turns do not count. At most one clarification per slot. A usable answer is retained as a report; a skip/unknown or a still-unclear answer after clarification becomes `Unknown`, without retaining arbitrary text as a fact. Raw replies remain only in the bounded transient transcript.

Questions establish units: dryer cycles over the confirmed bill period, cooling/pump hours per day, charging sessions per week, refrigeration units in total. Conservative deterministic recognition distinguishes usable, ambiguous, non-responsive and unknown answers. Unrecognised phrasing may become unknown after one clarification; this is not unrestricted natural-language understanding. Clarification Yes is accepted only when confirming an explicit proposal. An apartment description alone does not establish hot-water type; clarify own electric versus central supply. One total fridge/freezer overrides an earlier extra-unit selection; an explicitly additional unit or multiple total units permits extra-unit investigation. Mixed separate counts are clarified rather than silently summed.

Start with missing occupancy/major loads, then relevant reported systems (hot-water uncertainty, conditioning, scheduled pumps/charging, dryer, refrigeration). Skip known/skipped answers and absent equipment. Ask solar only without export/credit evidence, then useful period context. Do not add a filler priority question without reported loads. Final output selects up to three qualitative investigations, each with a priority phrase, reason, usable report, unknowns and next check. Normal single-unit refrigeration can be marked not enough evidence to prioritise. Ordering reflects investigation usefulness, not measured energy attribution. Operating checks and equipment information precede replacement; no appliance estimates or savings are added.

## General questions and memory

`POST /api/energy-assistant/chat`: `{mode:"general",messages:[{role:"user"|"assistant",content:string}]}`. Exactly these keys, 1–10 messages, last role user, 1–3,000 characters/message, 40,000 streamed request-byte limit. Browser composer caps new questions at 1,800 characters; follow-up answers at 1,000. Bill mode/PDF content is not accepted on this endpoint. Same-origin and no-store conventions apply. Success `{ok:true,answer:string}`; failure `{ok:false,message}` with 400 invalid, 413 size, 503 provider failure. Browser timeout 35 seconds.

The model gets only the recent bounded messages and existing reviewed guidance. Output is a strict `{answer:string}` object, 1–3,000 characters, qualitative only; digit/currency/percentage/URL output rejected. No live tools or numerical calculations. This is a general educational reply, not independently verified personalised advice. Existing library links provide source access separately.

`remember` caps transcript and general API context to ten most recent messages. Active confirmed bill and up to five household answers stay separately in component state so dropping earlier transcript messages doesn't lose answers or repeat questions. New chat aborts requests and clears all state; refresh/unmount resets. Stale results are discarded by request generation checks. No localStorage, cookies, database or cross-session memory. Server retains only request counters, not content. Provider access, failure, timeout and request limits never block the original seven-screen journey.

Both provider operations reuse `OPEN_AI_KEY`; no new key or environment variable. The existing `AI_DISTRIBUTED_LIMITS_CONFIRMED` guard applies when hosted on Vercel. Ten provider calls/client/minute and sixty/process, no bill-content caching. Limits are local demo controls, not measured distributed spend.

Rate extraction retains the printed AUD/cents unit in the provider-only strict schema. TypeScript divides cents by one hundred before producing the canonical AUD/kWh and AUD/day DTO; the model performs no rate arithmetic. Ambiguous rate units fail validation.
